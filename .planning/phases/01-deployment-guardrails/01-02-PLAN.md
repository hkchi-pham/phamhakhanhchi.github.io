<objective>
Rewrite `deploy.yml` so (a) every push to `main` deploys unless *all* its changed files are infrastructure/docs, and (b) the job refuses to publish a build whose `CNAME` is missing or wrong, and goes red if the live domain stops answering.

Purpose: this is the fix for the two silent failure modes at the heart of the phase. Today `_sass/_custom.scss` matches nothing in the allowlist, so every commit of Phases 2-7 would never reach the live site and no workflow would fail to say so. And nothing in the pipeline inspects `CNAME` before the deploy action force-pushes `gh-pages`.

Output: a `deploy.yml` with a `paths-ignore` denylist and two self-explaining guard steps, plus `bin/verify-cname.sh` as the single source of truth for the CNAME assertion.
</objective>

<research_corrections>
**The locked decision "invert the path filter to a denylist" cannot be implemented as an inverted `paths:` list.** GitHub's workflow syntax reference states: (a) you cannot use both `paths` and `paths-ignore` for the same event; (b) "If you define a path with the `!` character, you must also define at least one path without the `!` character. If you only want to exclude paths, use `paths-ignore` instead." An all-negative `paths:` list is rejected and the workflow never fires.

The decision is right; the implementation is `paths-ignore:`. **Delete the `paths:` key entirely.** If the word `paths:` still appears under `on.push` after this task, the task is wrong.

Decision rule to keep in mind while choosing entries: with `paths-ignore`, the workflow is skipped only when **ALL** changed paths in the push match the ignore list. A push touching both `.planning/FOO.md` and `_sass/_custom.scss` still deploys. That is the desired behaviour.

**The CNAME situation is currently HEALTHY, not broken.** Three deploys ran on 2026-09-11 (`599d45d`, `0d1b92e`, `f7b878d`), all after `CNAME` landed on `main`, and `origin/gh-pages:CNAME` is byte-identical to `main:CNAME` (blob `e4f56c9`, `phamhakhanhchi.com\n`). The live domain returns 200. So this guard is **regression insurance on a working pipeline**, not a repair. Phrase step names and the summary accordingly — never "restore the custom domain".

Further, reading `JamesIves/github-pages-deploy-action`'s own `src/git.ts`: when `_site/CNAME` is **absent**, the action adds `--exclude CNAME` to its `rsync --delete`, so the CNAME already on `gh-pages` survives. The genuinely uncovered hazard is therefore a **present-but-wrong** `_site/CNAME` (empty, truncated, or a different hostname) being rsynced over the good one. The assertion must check contents, not just existence — which is exactly what CONTEXT specifies.
</research_corrections>

Create `bin/verify-cname.sh` as the single source of truth for the CNAME assertion, so the workflow and the local test exercise the *same* code and cannot drift.

Contract:
- Takes one optional argument: the site directory (default `_site`). This is what makes it testable against a temp dir.
- Expected hostname `phamhakhanhchi.com`, defined once as a variable at the top.
- `set -euo pipefail` at the top — without it a typo in the guard silently succeeds, which is the same class of bug this phase exists to remove.
- Exit 0 when `<dir>/CNAME` exists and `tr -d '[:space:]' < <dir>/CNAME` equals the expected hostname.
- Exit 1 with a GitHub `::error title=...::` annotation in every other case. Two distinct messages:
  - **missing:** `::error title=CNAME missing - refusing to deploy::_site/CNAME was not produced by the build. Deploying now would hand gh-pages a site with no custom domain. Check that CNAME is still at the repo root and is not listed under exclude: in _config.yml.`
  - **wrong/empty:** `::error title=CNAME wrong - refusing to deploy::_site/CNAME contains '<actual>' but must contain 'phamhakhanhchi.com'. Deploying would overwrite the good CNAME on gh-pages and drop the custom domain.`
  (An empty file falls into the "wrong" branch with `<actual>` shown as empty — that is correct and readable.)
- On success, append a line to `$GITHUB_STEP_SUMMARY` if that variable is set, and echo the same line either way so it is useful when run locally. Guard the append: `[ -n "${GITHUB_STEP_SUMMARY:-}" ] && echo ... >> "$GITHUB_STEP_SUMMARY"` — do not let an unset variable abort the script under `set -u`.
- Use plain ASCII hyphens in the `title=` text (a literal em dash in an Actions annotation title is fine but ASCII keeps the file grep-friendly).
- Make it executable: `git update-index --chmod=+x bin/verify-cname.sh` after adding (this Windows checkout will not carry the mode bit otherwise, and the workflow calls it via `bash bin/verify-cname.sh` so the bit is belt-and-braces).

Then prove all four states locally. Write the check inline (do not commit a throwaway test file):

```bash
tmp="$(mktemp -d)"; mkdir -p "$tmp/_site"

printf 'phamhakhanhchi.com\n' > "$tmp/_site/CNAME"
bash bin/verify-cname.sh "$tmp/_site"; echo "good   -> $?"   # expect 0

printf 'phamhakhanhchi.com\r\n' > "$tmp/_site/CNAME"
bash bin/verify-cname.sh "$tmp/_site"; echo "crlf   -> $?"   # expect 0

: > "$tmp/_site/CNAME"
bash bin/verify-cname.sh "$tmp/_site"; echo "empty  -> $?"   # expect 1

printf 'example.com\n' > "$tmp/_site/CNAME"
bash bin/verify-cname.sh "$tmp/_site"; echo "wrong  -> $?"   # expect 1

rm -f "$tmp/_site/CNAME"
bash bin/verify-cname.sh "$tmp/_site"; echo "absent -> $?"   # expect 1
```

Record the five exit codes in the plan SUMMARY. Do NOT test by breaking the real `CNAME` — the domain is currently healthy and must stay that way.

Make four changes to `.github/workflows/deploy.yml`. Leave every existing build step, action version and pin exactly as it is.

**(a) Replace the trigger block.** Delete BOTH `paths:` lists and the entire `pull_request:` trigger. The Deploy step is already `if: github.event_name != 'pull_request'`, so the PR half only ever produced a build-without-deploy smoke test, and this project pushes direct to `main` (locked decision: no branch-per-phase, no reviewer). One list is better than two kept in sync. Also drop `master` from `branches:` — this repo has no `master`.

```yaml
name: Deploy site

on:
  push:
    branches:
      - main
    # DENYLIST, not an allowlist. Every push to main deploys unless EVERY
    # changed file in the push matches a pattern below.
    #
    # The previous allowlist ("assets/**", "**/*.md", "**.yml", ...) never
    # listed _sass/**, so a commit touching only _sass/_custom.scss silently
    # never reached the live site — with no failed workflow to signal it.
    # An allowlist would have re-broken for the next unlisted file type
    # (fonts, .json data, images), so the shape is inverted rather than patched.
    #
    # Note: `paths` and `paths-ignore` are mutually exclusive, and GitHub
    # rejects a `paths:` list made only of `!` exclusions — `paths-ignore`
    # is the only supported way to express this.
    paths-ignore:
      - ".planning/**"
      - "docs/**"
      - "lighthouse_results/**"
      - ".github/**"
      - "README.md"
      - "AGENTS.md"
      - "CLAUDE.md"
      - "LICENSE"
      - ".prettierignore"
      - ".prettierrc"
      - ".gitignore"
  workflow_dispatch:

concurrency:
  group: deploy-gh-pages
  cancel-in-progress: false
```

Do NOT add `tags:` — `design-*` tags must not trigger deploys.

Be aware of the consequence and do not fight it: `.github/**` is ignored, so editing `deploy.yml` itself does not deploy. That is deliberate (a workflow edit should not republish the site), and it means you cannot prove this file works by pushing it. Use the already-present `workflow_dispatch`, and let plan 04's separate `_sass`-only commit be the real proof.

**(b) Insert the CNAME gate** between the "Purge unused CSS 🧹" step and the "Deploy 🚀" step. It must precede the deploy because the deploy is a destructive force-push; a guard after it would report a disaster instead of preventing one.

```yaml
      - name: Verify CNAME before deploying 🔒
        run: bash bin/verify-cname.sh _site
```

**(c) Append the live-domain check** after the "Deploy 🚀" step:

```yaml
      - name: Verify live domain responds 🌐
        run: |
          set -uo pipefail
          url="https://phamhakhanhchi.com"
          code=000
          for attempt in $(seq 1 12); do
            code="$(curl -s -o /dev/null -w '%{http_code}' -L --max-time 20 "$url" || echo 000)"
            echo "attempt ${attempt}: ${code}"
            if [ "$code" = "200" ]; then
              echo "Live domain OK (${url} -> 200)" >> "$GITHUB_STEP_SUMMARY"
              exit 0
            fi
            sleep 15
          done
          echo "::error title=Live domain not responding::${url} did not return 200 within ~3 minutes of deploying (last status ${code}). Check Settings > Pages still shows the custom domain, and that gh-pages still has a CNAME file."
          exit 1
```

Note the deliberate details: `set -uo pipefail` **without** `-e`, and `|| echo 000` on the curl, so a DNS failure stays inside the retry loop instead of aborting on the first attempt. 12 x 15s is ~3 minutes — CONTEXT said "roughly 60s"; the extra headroom absorbs GitHub's separate "pages build and deployment" run, which this job does not wait on, and removes the main cry-wolf risk.

Add a short comment above this step recording what it does and does not prove: it asserts the domain **resolves** (catching DNS loss, custom-domain unset, Pages disabled). It does not prove new content is live — the served CSS carries `Cache-Control: max-age=600` behind a CDN. Proving content shipped is the job of the marker grep in plan 04 and of `docs/DEPLOYMENT.md`'s by-hand recipe.
