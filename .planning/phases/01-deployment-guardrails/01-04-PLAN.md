<why_this_marker_shape>
- **A comment alone proves nothing.** Sass strips `//` comments entirely, and Jekyll's minifier may strip `/* */` too. The proof must be a *declaration*.
- **`:root` survives PurgeCSS on this exact config**, verified two ways: `purgecss.config.js` does not set `variables: true`, so custom-property removal is off by default; and the CSS served from the live domain today already begins `:root{color-scheme:light;--global-bg-color: #ffffff;...}`.
- **A custom property nothing references is invisible.** It repaints nothing. The phase requires the site to be pixel-identical when it ends, and this satisfies that.
- **The cache-buster is mandatory.** `main.css` is served with `Cache-Control: max-age=600` behind a CDN (`x-proxy-cache` header present). Without `?cb=$(date +%s)` you will grep a stale copy and wrongly conclude the deploy failed.
- **`_sass` is not in `deploy.yml`'s `paths-ignore` list**, which is precisely why this push must fire. If it does not fire, the denylist is wrong — go back to plan 02, do not patch around it.
</why_this_marker_shape>

<why_the_old_filter_did_not_catch_this_before>
`.entry-year` is defined only in `_sass/_custom.scss` and IS already present in the live CSS. That is not a contradiction of SAFE-01: the commits that introduced those rules also touched `_pages/*.md`, which matched `"**/*.md"` in the old allowlist, and any triggered build compiles the whole site including `_sass`. The bug fires only for a commit touching **nothing but** `_sass/**` — which is every commit of Phases 2-7.

Therefore: if the proof commit's diff contains any second file, the test is vacuous. `git show --stat HEAD` must show exactly one path.
</why_the_old_filter_did_not_catch_this_before>

**Step 1 — Wait for `gh-pages` to advance.** Poll rather than sleeping blindly; the run needs a few minutes for Ruby/Node setup, the Jekyll build, PurgeCSS and the deploy:

```bash
for i in $(seq 1 20); do
  now="$(git ls-remote origin refs/heads/gh-pages | cut -f1)"
  echo "poll $i: $now"
  [ "$now" != "$before" ] && { echo "gh-pages advanced: $before -> $now"; break; }
  sleep 30
done
```

`gh-pages` advancing is stronger evidence than a green tick and needs no `gh` CLI (which is not installed here). If it has not advanced after ~10 minutes, STOP and diagnose — do not patch around it:
- Check the Actions tab in a browser. If no "Deploy site" run exists at all, the `paths-ignore` list is wrong — some pattern is matching `_sass/**`. Fix plan 02's list; do not add `_sass` to an allowlist.
- If a run exists and failed on "Verify CNAME before deploying", that is the guard working: read the `::error` line, which names the problem.

**Step 2 — Confirm the deploy commit references your commit.** `git log -1 --format=%s origin/gh-pages` (after `git fetch origin`) should read `Deploying to gh-pages from ...@<your sha>`.

**Step 3 — Grep the served CSS, with the cache-buster.** This is the part that proves the change survived PurgeCSS and the CDN, not merely that a workflow ran:

```bash
for i in $(seq 1 12); do
  n="$(curl -s "https://phamhakhanhchi.com/assets/css/main.css?cb=$(date +%s)" | grep -c -- "--deploy-proof")"
  echo "css poll $i: $n"
  [ "$n" -gt 0 ] && break
  sleep 30
done
```

Allow several minutes: GitHub's "pages build and deployment" is a *separate* run this workflow does not wait on, and the asset carries `max-age=600`. A count of 0 while the HTML's `Last-Modified` has moved is the classic PurgeCSS-stripped signature — but `:root` custom properties are verified to survive this config, so treat 0 after 6+ minutes as a real failure to investigate, not as expected.
