  <action>
Create `.planning/phases/01-deployment-guardrails/verify.sh`: a POSIX-ish bash script that composes every automatable row of RESEARCH.md's "Phase Requirements -> Test Map" into one command. It exists so criteria are repeatable, NOT so a test framework exists — do not add a framework, a config file, or an npm script. (An `npm run` entry for this would drift toward the starter-local build pipeline the project forbids.)

Structure:
- `set -uo pipefail` (not `-e` — the script must run every check and report a tally, not abort on the first red).
- A `check <label> <command...>` helper that prints `PASS`/`FAIL` per row and increments a failure counter. Exit 0 only if the counter is 0.
- Two blocks. The **static** block always runs. The **live** block runs only when invoked as `bash verify.sh --live`, so the script is usable before the proof push exists.
- Print a final tally line: `N checks, M failed`.
- Run from the repo root; the script should `cd "$(git rev-parse --show-toplevel)"` at the top so it works from anywhere.

**Static block** — one `check` per row:

| Req | Assertion |
|-----|-----------|
| SAFE-01 | `grep -q 'paths-ignore:' .github/workflows/deploy.yml` |
| SAFE-01 | `! grep -qE '^\s+paths:' .github/workflows/deploy.yml` (an all-negative `paths:` list would never fire) |
| SAFE-01 | `! grep -qE '^\s+- "?_sass' .github/workflows/deploy.yml` (`_sass` must NOT be ignored) |
| SAFE-02 | `bin/verify-cname.sh` exits 0 on a good temp CNAME and 1 on empty / wrong / absent (the four-state fixture from plan 02, inlined here with `mktemp -d`) |
| SAFE-02 | the `bin/verify-cname.sh` line number in `deploy.yml` is LESS than the `JamesIves/github-pages-deploy-action` line number |
| SAFE-02 | the `Verify live domain responds` line number is GREATER than the deploy-action line number |
| SAFE-02 | repo-root `CNAME` still normalises to `phamhakhanhchi.com` (`tr -d '[:space:]' < CNAME`) |
| SAFE-03 | `test ! -f .github/workflows/visual-regression.yml` |
| SAFE-03 | the basenames of `.github/workflows/*.yml` sort to exactly `broken-links-site.yml deploy.yml prettier.yml` |
| SAFE-04 | `test -f docs/DEPLOYMENT.md` and it greps case-insensitively for `path filter`, `CNAME` and `PurgeCSS` |
| — | `npx prettier . --check --end-of-line auto` exits 0 |

The SAFE-04 rows will FAIL until plan 05 lands. That is correct and expected — say so in a comment at the top of the block so nobody "fixes" it by deleting the check. Note in the same comment that the `docs/DEPLOYMENT.md` grep is a **presence proxy only**: whether the doc actually states that a `_sass`-only revert now redeploys is a prose claim that a human must read, and it is listed as manual-only in `01-VALIDATION.md`.

**Live block** (`--live`):

The `--deploy-proof` row will FAIL until plan 04 lands; the tag row until plan 05. Comment that too.

Make the script executable (`git update-index --chmod=+x`).

This is the phase's first remote mutation. Do it carefully.

**Step 1 — Pre-flight.** Never `--force`. Check the remote has not moved:

```bash
git fetch origin --prune --tags
git log --oneline origin/main..main          # your commits, expect ~14
git log --oneline main..origin/main          # MUST be empty
```

If `main..origin/main` is non-empty, a bot or another session moved the remote. `git pull --rebase` and re-run `bash .planning/phases/01-deployment-guardrails/verify.sh` before continuing. Do not force-push under any circumstance.

**Step 2 — Record the "before" value** that criterion 1 is measured against:

```bash
git ls-remote origin refs/heads/gh-pages | cut -f1    # expect f7b878d... — write this down
```

**Step 3 — Gate on green.** `bash .planning/phases/01-deployment-guardrails/verify.sh` must show FAILs only in the SAFE-04 rows, and `npx prettier . --check --end-of-line auto` must exit 0. Do not push otherwise.

**Step 4 — Push.** Either a single `git push origin main`, or the two-step split described in `<expected_push_behaviour>` if you want to observe the "no deploy" case cleanly. State which you chose.

**Step 5 — Observe.** `gh` is not installed, so read the outcome from the remote refs rather than from run status:

- Re-run `git ls-remote origin refs/heads/gh-pages | cut -f1` after ~4 minutes. Compare with step 2.

**Step 6 — Record** in the SUMMARY: which push shape you used, the gh-pages SHA before and after, whether a deploy fired and whether that matched the prediction, and the live HTTP status.
