  <name>Task 1: Set the site in Literata, the labels in Be Vietnam Pro, and unsplit the name</name>
  <files>_sass/_custom.scss</files>
  <action>
Extend the fenced "gem behaviours no token can reach" section of `_sass/_custom.scss` with
a new numbered override group. Keep every existing convention: each rule annotated with the
gem source line it corrects, no `!important`, and **no colour or length literal** — every
value a `var()` into `_tokens.scss`.

**1a — the one declaration that sets the whole site.**

```scss
body {
  font-family: var(--font-serif);
  font-size: var(--step-1);
  font-weight: 400;
  line-height: var(--leading-body);
}
```

The comment must carry three facts, because each one is a trap:

1. It beats `@layer base { body { font-family: Roboto, sans-serif } }` because `main.css`
   is unlayered and loads last — the same mechanism as the six overrides above it.
2. `h1`-`h6` take `font-family: inherit` from that same base layer, so **this single
   declaration also makes every heading serif.** That is the whole "headings are serif
   throughout" decision; do not write six per-heading `font-family` rules.
3. **`font-weight: 400` is NOT redundant.** The gem sets 300, and with only 400/600 faces
   loaded, 300 silently resolves to the 400 face — so nothing looks broken, and that is
   exactly why it would go unnoticed if it propagated to `h1`/`h2`.

**1b — the weight lever.** CONTEXT locks weight as the second hierarchy lever alongside
Phase 2's ink depth, and Phase 7's greyscale-plus-blur test needs it: `h1` and `h2` get
`font-weight: 600`, `h3` gets `font-weight: 400`, and headings take
`line-height: var(--leading-heading)`. Explicit, because Tailwind's
`h1,h2,h3,h4,h5,h6{font-weight:300}` would otherwise leave every heading at 400 and the
locked 600 would never render. The size tokens carry nothing about weight.

**1c — the sizes.** `h1` and `.post-title` take `var(--step-5)`; `h2` takes `var(--step-4)`;
`h3` takes `var(--step-3)`; `h4` takes `var(--step-2)`. `.entry-title` already reads
`--step-2` and needs no change. Use `--space-*` for heading margins if the gem's
`margin-bottom: .5rem` reads wrong at the new sizes — that is Claude's discretion per
CONTEXT, and it must come from the space scale, never from a literal.

**1d — the companion face, on labels only.** Point `.entry-year`, `.entry-meta` and
`.subject-grade` at `var(--font-sans)` (these three rules already exist in `_custom.scss`;
add the declaration). Add a new rule pointing `.nav-link` at `var(--font-sans)`.

Comment it as navigational furniture — the same reasoning Phase 2 used to leave nav links
deliberately un-underlined. Note also that the gem's `font-weight: bolder` on `.nav-link`
resolves to 600 against the loaded 400/600 faces, which is the Be Vietnam Pro 600 cut, so
it is consistent rather than faux-bold. **Leave `font-weight: bolder` alone** — it is the
active-nav marker Phase 2 chose precisely because it is non-colour and survives greyscale.

`.entry-status`: follow 03-01's answer (see the decisions block above).

**Nothing else gets the sans.** The division CONTEXT states is body-and-headings serif,
labels-years-metadata-status sans. Do not spray `var(--font-sans)` at anything not named
here — criterion 3's "no third type family" grep is a proxy for register discipline, and a
sans creeping into body-adjacent text is the failure it exists to prevent.

**1e — code.** Write NO rule. `pre`/`code` receive no `font-family` from `main.css` at all,
and the gem's only `Iosevka Fixed` declaration targets `.typogram`, which no page on this
site renders. Code already resolves to the browser's monospace default. An override
targeting `.typogram` would be purged anyway. The decision is recorded in `_tokens.scss`'s
cap comment by plan 03-02; do not manufacture a dead rule here to make it look implemented.

**1f — the TYPE-03 hazard nobody wrote down.** On the six inner pages the navbar brand
renders the family name inside a `.font-weight-bold` span, within a `.navbar-brand` that
carries `.font-weight-lighter`. The bold class forces 700, which matches the 600 face, while
the rest of the name inherits the lighter weight — so **the family name renders heavier
than the rest of the name on six of seven pages.** That is the same one-name-two-appearances
failure TYPE-03 exists to prevent, expressed in weight instead of typeface. It is invisible
today only because Roboto's variable font makes the step small. Extend the existing
override rather than adding a second one, so `.post-title .font-weight-bold` and
`.navbar-brand .font-weight-bold` both take `font-weight: inherit`.

Also declare `.navbar-brand { font-family: var(--font-serif); }` so the brand is provably
Literata rather than inheriting it by luck — CONTEXT locks both appearances of the name to
one face, and an explicit declaration makes that a `--live` grep instead of an assumption.
`font-weight-bold` is already in the PurgeCSS safelist and `.navbar-brand` is in the built
HTML, so both nodes survive.

Note for the summary: **the brand does not render on the home page at all.** CONTEXT says
"the name appears in two places"; that is true page-by-page, but the two places are never
both visible at once. Correct the record rather than repeating it.

<task type="auto">
  <name>Task 2: Give the prose its measure, and safelist it in the same commit</name>
  <files>_sass/_custom.scss, purgecss.config.js</files>
  <action>
**These two files change together in ONE commit.** That is not tidiness — a measure rule
that ships with `ol`, `blockquote` and `h4` pruned out of its selector list is a rule that
is correct in source and wrong in production, with no error anywhere. Phase 2 shipped
exactly that failure and it took a day to find.

**2a — the selector list.** CONTEXT asks for the measure on `p`, `h1`-`h6`, `ul`, `ol`,
`blockquote` "inside `.post article`" while excluding `.entry-list`, `.subject-list`,
`.topic-list`, CV blocks and tables. **Those two clauses contradict each other under a
descendant selector**, because the entry pages nest `h2.entry-group-title` and
`h3.entry-title` inside `<article>`. And a plain child combinator misses the home page
entirely, because its prose sits in `<div class="clearfix">`. Resolve it with an explicit
two-level child list:

```scss
.post article > p,
.post article > ul,
.post article > ol,
.post article > blockquote,
.post article > h2,
.post article > h3,
.post article > h4,
.post article > .clearfix > p,
.post article > .clearfix > ul,
.post article > .clearfix > ol,
.post article > .clearfix > blockquote,
.post article > .clearfix > h2,
.post article > .clearfix > h3,
.post article > .clearfix > h4 {
  max-width: var(--measure);
}
```

(Add the two `header.post-header` selectors only if 03-01 answered `title-measured`.)

Verbose on purpose. Every consequence is visible and every selector is greppable in the
served CSS, which is this project's established discipline. The child combinators guarantee
`section.entry-group > h2`, `.entry-body > h3`, `.card-body > p` and the subject rows are
untouched, satisfying the exclusion clause exactly.

**Do NOT collapse this with `:is()`.** `.post article > :is(p,ul,ol,...)` is shorter and
works in browsers, but this project has never exercised PurgeCSS's selector-node analysis
of `:is()` and the failure mode is silent. The explicit list is known to degrade
node-by-node in a way the safelist can correct.

Use `max-width` alone — no auto margins. The column stays left-aligned against the page's
left edge, which is what puts the ~354px gutter on the right where Phase 4's marginalia
will live.

The comment on this rule must record: the two-level structure and why each level exists;
that `h1.post-title` and `p.post-description` live in `header.post-header`, a SIBLING of
`article`, and therefore keep the full 930px (or do not, per 03-01's answer); and that on
`/cv/` and `/further-reading/` a `p.entry-detail` IS a direct child of `article` and so
does pick up the measure — which is correct, it is prose.

**2b — the safelist.** Add `"ol"`, `"blockquote"` and `"h4"` to `purgecss.config.js`'s
`safelist` array, with a comment in the style of the existing `":focus-visible"` and
`"h5"`/`"h6"` entries. The comment must say: the prose-measure selector list names these
three; none appears in ANY built page today, so PurgeCSS drops those nodes from the list
and the rule ships incomplete — silently, with the source still correct. Cite the standing
live proof: `_custom.scss` declares `.topic-list` and the served `main.css` contains zero
occurrences of it.

Do not remove or reorder any existing entry. `":focus-visible"` keeps its leading colon —
without it there is no match, measured against purgecss 8.0.0, and the site loses its
keyboard focus ring again.

Note for the summary: `pre,code{color:var(--ink-800)}` survives purging today only because
the literal words "pre" and "code" happen to appear in page text and PurgeCSS's default
extractor matches bare tag selectors against any word token. That is luck, not a rule, and
it is why `h4`, `ol` and `blockquote` get explicit entries rather than a hope.

**2c — do not touch `.al-folio-overrides.yml`.** Its hash covers `assets/css/main.scss`,
which this plan does not modify. Confirm with `git status` rather than assuming.
