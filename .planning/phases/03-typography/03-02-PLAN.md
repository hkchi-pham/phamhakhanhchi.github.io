**1a — the fonts URL.** Replace the value of `third_party_libraries.google_fonts.url.fonts`
(currently line 542) with the css2 request for the locked five cuts:

```yaml
  google_fonts:
    url:
      fonts: "https://fonts.googleapis.com/css2?family=Be+Vietnam+Pro:wght@400;600&family=Literata:ital,wght@0,400;0,600;1,400&display=swap"
```

(Drop `;1,400` and the `ital,` prefix if 03-01 answered **status-sans**.)

Three things to get right and one myth to not repeat:

- `display=swap` is KEPT. Text must always be visible; `display=optional` was considered
  and rejected because a cold-cache first visit could render the whole typography phase in
  the fallback.
- This edit is what drops **Material Icons** and both **Roboto** families — they are named
  only in the string being replaced.
- The `&` is emitted HTML-escaped as `&amp;` by the gem's `<head>`; browsers parse that
  correctly. `;` and `@` pass through a YAML double-quoted string unchanged. Both are
  nevertheless asserted by a `--live` row after the push, because this is exactly the kind
  of thing worth proving rather than assuming.
- **Do NOT add preconnect, preload or a `font-display` key, and do NOT flip
  `third_party_libraries.download`.** 03-RESEARCH Finding 12 settled this: no such config
  key exists, the `<head>` is gem-owned and emits the fonts link as
  `<link defer rel="stylesheet">` (`defer` is inert on `<link>`), and `download` is global
  to ALL third-party libraries — flipping it would self-host Font Awesome, bootstrap-table,
  MathJax and highlight.js in one move and create `assets/webfonts/`. `display=swap` plus
  metric-close fallbacks is the entire loading strategy available to this phase. Record
  this as a deliberate non-action in the summary, not as an oversight.

**1b — the dead icon CDNs.** Delete the `academicons:` and `scholar-icons:` blocks from
`third_party_libraries` (each is an `integrity`/`url`/`version` trio). They render nothing:
`_data/socials.yml` has only `email` active, and there are zero `ai-` and zero `si-`
classes anywhere in the built site. Removing them saves 14,063 B and two render-blocking
requests for zero visual change.

**Keep `fontawesome:`** — the one envelope icon uses it. Replacing that envelope with
inline SVG is explicitly deferred to Phase 6.

**Known risk, and its containment.** The gem's `<head>` include may read these keys
unconditionally. Two possible outcomes, both handled: (i) the Jekyll build errors, in which
case `deploy.yml` fails BEFORE publishing and nothing reaches visitors — restore the two
blocks and record the finding; (ii) the build succeeds but emits
`<link rel="stylesheet" href="">`, which is harmless but wrong — `verify.sh` already
carries a `--live` row asserting the served HTML has no empty stylesheet href, and the fix
is again to restore the two blocks. There is no local Jekyll here to pre-check this, so it
is caught at the push in plan 03-04, deliberately.

**1c — leave `max_width` alone.** Line 106 reads `max_width: 930px` and it STAYS. CONTEXT
locks the page width and measures the prose instead; the ~354px left over is the gutter
Phase 4's marginalia and Phase 5's PAGE-06 will use. `verify.sh` carries an unlabelled
green row asserting this, precisely so a well-meaning later narrowing shows up as a
failure.


Comment must record: Georgia is −5% on x-height against Literata where Times New Roman is
−12%, so the order is measured rather than alphabetical; and that the sans fallbacks are
~9% narrower than Be Vietnam Pro, which is acceptable because the sans only ever carries
short labels and years, never a wrapped paragraph.

Also write, in that same comment, the sentence that makes criterion 3 auditable: **there
is no rule anywhere declaring a monospace family**, because the gem's only `Iosevka Fixed`
declaration targets `.typogram`, which no page on this site renders, and `pre`/`code` get
no `font-family` at all from `main.css`. Code already falls back to system mono today.
Manufacturing a dead override to make the decision "look implemented" is explicitly
rejected — it would also be purged, since no built page contains `.typogram`.

**2c — the scale, as `calc()` not as literals.** Re-point `--step-0`..`--step-3` and add
`--step-4`, `--step-5`:

```scss
  --step-1: 1.0625rem;                      /* body, 17px on a 16px root */
  --step-0: calc(var(--step-1) * 0.85);     /* meta, status                     */
  --step-2: calc(var(--step-1) * 1.15);     /* .entry-title, h4                 */
  --step-3: calc(var(--step-1) * 1.35);     /* h3  — TYPE-04 floor is 1.25      */
  --step-4: calc(var(--step-1) * 1.8);      /* h2  — TYPE-04 floor is 1.5       */
  --step-5: calc(var(--step-1) * 2.6);      /* h1, .post-title                  */
```

**The `calc()` form is not a style preference — it is what makes criterion 4 automatable.**
"H2 is at least 1.5x body size and H3 at least 1.25x" becomes a `verify.sh` row grepping
the SERVED css for `--step-4:calc(var(--step-1)*1.8)`. With literal rems the ratio is only
recoverable by dividing two numbers a reader has to trust, and `0.903125rem` /
`1.434375rem` invite a future "tidy-up" to `0.9rem` that silently moves the ratio. This
site has no browser-based test framework; a greppable ratio is the difference between an
automated row and a manual one.

`--step-4` and `--step-5` are NEW NAMES, not re-tuned values. The block comment above the
scale currently says the names are locked and only the values are Phase 3's to move —
**update that comment** to record that this phase added two names deliberately, and why
(the decisive 2.6/1.8 scale needs steps the provisional four did not have).

Sass safety: Dart Sass parses custom-property values as unquoted strings and passes them
through verbatim, so `calc(var(--step-1) * 1.8)` survives compilation. Whether compressed
output keeps the spaces around `*` is not checkable without a local build, which does not
exist here — which is why every `verify.sh` grep for these is whitespace-tolerant.

**2d — leading and the measure.**

```scss
  --leading-body: 1.6;      /* was 1.5 — the gem's value, tuned for Roboto at 16px across a wide column */
  --leading-heading: 1.2;   /* matches what tailwind's base layer already ships; the token makes it ownable, not different */
  --measure: 36rem;         /* 576px */
```

The `--measure` comment must carry the arithmetic, because it is the only evidence
criterion 4's 45-75 window is met by design rather than by luck: Literata's `xWidthAvg` is
0.480em, so at 17px the column holds 576 / (0.480 x 17) = **~70.6 characters** — inside the
window, with the margin one-sided in our favour because ragged-right wrapping makes real
lines shorter. If a deployed measurement ever comes back over 75, the fix is `34rem`
(544px -> 66.7). Record too that 930px minus 576px leaves ~354px, and that this gutter is
deliberate: Phase 4's marginalia and Phase 5's PAGE-06 live there. This phase creates it
and puts nothing in it.

**2e — what NOT to do here.** Do not re-point `--underline-offset`. It is `0.18em`, tuned
and human-approved in Phase 2 against **Roboto's** descenders, and Literata's descenders
are ~26% deeper relative to em (−308/1000 vs −500/2048). That makes a collision with `ạ`/`ợ`
more likely than not — but it is a browser observation, not a computation, and
03-RESEARCH is explicit: do not re-tune blind. It is checked at plan 03-04's human
checkpoint and re-pointed there if it collides.

Discipline carried forward from Phase 2, unchanged: no comment in `_sass/` may spell out a
string the harness asserts is absent, and no `!important` anywhere.
