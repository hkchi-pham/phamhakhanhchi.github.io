<objective>
Create the single token file the whole design reads from, and wire it into the stylesheet so it is emitted after the gem's `_themes.scss` but before the site's `_custom.scss`.

Purpose: this is the mechanism behind the entire phase. The gem's prebuilt `assets/css/tailwind.css` cannot be recompiled, but it *consumes* `var(--global-*)` without defining any of them; `main.css` is the sole definition site and is unlayered and last in `<head>`. Re-pointing those 30 names is the only thing that reaches both stylesheets, so there is no intermediate state where the navbar is cream and the cards are still white.

Output: `_sass/_tokens.scss` (Tier 1 primitives + written cap + Tier 2 semantic map), one added `@use` line in `assets/css/main.scss`, and a hand-recomputed `local_sha256`.
</objective>

    :root,
    html[data-theme="dark"] {

**The selector list is load-bearing and must not be collapsed to `:root`.** CSS specificity is computed per selector in a list, not for the list as a whole. For an element matching `html[data-theme="dark"]` our winning selector is (0,1,1) — identical to the gem's block at `_themes.scss:76`, which is compiled into `main.css` unconditionally regardless of `enable_darkmode` — and ours is emitted later in the same stylesheet, so it wins. This is what makes success criterion 2's second clause ("forcing `data-theme="dark"` in DevTools changes no colour") true. Flipping the config flag alone does **not** do it.

`color-scheme: light` must be re-declared inside the block: the gem's dark block sets `color-scheme: dark`, which changes scrollbar and form-control rendering even when every colour token is overridden.
