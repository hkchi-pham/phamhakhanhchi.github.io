## Why the safelist, and not a selector rewrite

02-VERIFICATION.md offered two fixes. This plan takes the safelist. Both were
measured on 2026-09-15 against **purgecss 8.0.0** (the version CI installs —
`npm install -g purgecss`, unpinned) using the Node API on a fixture that
reproduces this site's markup. Results, verbatim:

| Candidate | Outcome |
| --- | --- |
| `:focus-visible { … }`, no safelist | **STRIPPED** — reproduces the live bug exactly |
| safelist `":focus-visible"` (leading colon) | **KEPT**, whole rule, unchanged |
| safelist `"focus-visible"` (no colon) | **STRIPPED** — does not match |
| safelist regex `/:focus-visible/` | KEPT |
| `*:focus-visible { … }`, no safelist | KEPT (universal selector is always kept) |
| `a:focus-visible, button:focus-visible, .btn:focus-visible, input:focus-visible, [tabindex]:focus-visible` | rule kept, but PurgeCSS **deletes `input:focus-visible` and `[tabindex]:focus-visible` from the list** — neither token exists in the built HTML |

The safelist wins on three counts:

1. **Coverage is preserved.** The concrete-selector rewrite measurably loses
   two of its five selectors on this site's HTML today (`input`, `[tabindex]`
   — the home page contains zero of each), and would silently lose more as
   the markup changes. The bare rule covers every focusable element, now and
   in Phase 5/6 when new components arrive.
2. **It fixes the cause where the cause lives.** 02-VERIFICATION.md's
   anti-pattern table names `purgecss.config.js` lines 6-26: a safelist of
   class names with no entry for a pseudo-class-only selector. The next agent
   who writes `:target` or `:focus-within` reads that file, not a comment
   buried in SCSS.
3. **`_sass/_custom.scss` is not touched at all.** Criterion 5 (every literal
   in one token file) and must-have #19 (`_custom.scss` carries no literal)
   therefore stay true by construction rather than by re-verification, and the
   deploy becomes a clean single-variable experiment: the only source file
   that changes is the PurgeCSS config, so if the rule appears in the served
   CSS afterwards, the safelist is unambiguously why.

Rejected: `*:focus-visible`. It works, but it is a one-character workaround
whose reason survives only in a comment, and it teaches nothing to the next
bare-pseudo-class rule.

## h5 / h6 — taken, because this fix makes it free

Must-have #17 notes that PurgeCSS also drops `h5`/`h6` from the heading-ink
rule (`h1,h2,h3,h4,.post-title{color:var(--ink-900)}` is what production
serves today — confirmed by `curl`). The verifier deliberately did not score
it. Because the chosen fix is already a safelist edit, protecting it costs two
strings and was measured in the same probe: safelisting `"h5"` and `"h6"`
restores them to the selector list. Side effect, stated honestly: any *gem*
rule whose selector carries an h5/h6 tag node is also retained. That is a few
bytes and zero visual change (no page renders those tags), and it means a
future `<h5>` inherits heading ink without a config change. Taken.

Not taken, and deferred instead: pinning `purgecss` in `deploy.yml` (it is
installed unpinned, so a future major could change safelist semantics under
us). Out of scope here; the new `--live` rows are what catch it if it happens.
Record it in `deferred-items.md` only if you are already editing that file.
